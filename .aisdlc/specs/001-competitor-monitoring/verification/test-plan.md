# Lensmor Monitor v1.0.0 完整测试计划

## 0. 执行摘要

| 项目 | 说明 |
|---|---|
| **待测能力** | Lensmor Monitor MVP（竞品监控平台）：竞对列表管理、自动数据采集、变化检测、日报生成与邮件投递 |
| **版本** | v1.0.0 |
| **发布日期** | 2026-06-17 |
| **目标受众** | 内部竞品分析团队（初期 5–10 人） |
| **关键目标** | 验证所有 AC（AC-001~AC-007）通过；验证系统可靠性（采集率 > 95%、邮件送达率 > 99%、变化精准度 > 95%）；确认性能满足 10 并发竞对场景 |

## 1. 测试范围

### 1.1 In Scope（含）

**功能范围：**
- ✅ 竞对列表管理（CRUD 操作、表单验证、删除确认）
- ✅ 数据采集（爬虫脚本、定时任务、重试机制、成功率统计）
- ✅ 变化检测（完全一致比对、字段级变化识别、变化类型分类）
- ✅ 日报生成（按模板生成、按竞对分组、仅包含有变化的竞对）
- ✅ 邮件投递（定时发送、多收件人、投递成功/失败统计）
- ✅ 日报查看（Web 界面、邮件链接跳转、历史日报查询）

**测试类型：**
- 功能测试（所有 AC 验证）
- 集成测试（端到端流程：竞对 → 采集 → 检测 → 日报 → 邮件）
- 性能测试（10 竞对并发采集、API 响应时间、邮件批量投递）
- 可靠性测试（采集失败重试、邮件投递失败处理、数据一致性）
- 用户验收测试（易用性评分、内容质量反馈）

**非功能需求：**
- 系统可用性 >= 99%
- 采集成功率 > 95%
- 邮件送达率 > 99%
- 变化检测精准度 > 95%
- API P95 响应时间 < 200ms
- 邮件投递延迟 < 5 分钟

### 1.2 Out of Scope（不含）

- ❌ 用户认证与权限管理
- ❌ 高级搜索/筛选/维度组合
- ❌ AI 自动分析生成
- ❌ 实时采集与推送
- ❌ 第三方数据服务集成
- ❌ 移动端适配（仅桌面 Web）

## 2. 测试策略

### 2.1 测试层次与方法

| 层次 | 方法 | 覆盖范围 | 工具/框架 |
|---|---|---|---|
| **单元测试** | 正向/反向/边界测试 | 核心模块（采集、变化检测、日报生成） | Jest + 模拟对象 |
| **集成测试** | 端到端流程验证 | 完整业务链路（竞对 → 邮件） | Supertest + 测试数据库 |
| **系统测试** | 功能完整性、错误处理 | 所有 AC + 非功能需求 | 手工 + 自动化脚本 |
| **性能测试** | 并发负载、响应时间 | 10 竞对采集、邮件批量投递、API 吞吐 | k6 / Apache JMeter |
| **用户验收测试** | 真实用户试用、满意度评分 | UI 易用性、内容质量、邮件体验 | 手工 + 问卷 |

### 2.2 测试策略（用例设计）

**正向路径：**
- 用户创建竞对 → 系统自动采集 → 检测到变化 → 生成日报 → 发送邮件 → 用户查看

**反向路径（错误处理）：**
- 无效竞对 URL → 采集失败 → 重试 → 最终失败 → 记录错误日志
- 邮件服务不可用 → 邮件投递失败 → 重试 → 最终失败 → 告警

**边界条件：**
- 0 竞对（无采集）、1 竞对、10 竞对、50+ 竞对（超出 MVP 设计）
- 网页内容大小：< 1MB、1–10MB、> 10MB
- 竞对数据变化：0 处、1 处、> 100 处（极端变化）

## 3. 环境与数据准备

### 3.1 测试环境

| 环境 | 配置 | 用途 |

| **本地开发** | 本机 Node.js、PostgreSQL、React | 开发调试、单元测试 |

| **生产预发** | 云服务器（2 核 4GB）+ RDS PostgreSQL | UAT 和上线前验证 |

### 3.2 数据准备

**测试竞对网站：**
- `https://example.com`（静态 HTML 页面）
- `https://example2.com`（动态 JavaScript 渲染）
- `https://example3.com`（API 驱动内容）
- 备选：实际竞对网站 3–5 个（需获得访问授权）

**测试用户邮箱：**
- 内部测试账号 5–10 个（@company.com）

**测试数据集：**
- 初始化竞对列表（10 个）

- [ ] 前端能访问（`http://localhost:3000`）
- [ ] 数据库连接验证（查询 competitors 表返回结果）
- [ ] SendGrid / SMTP 邮件发送测试（发 1 封测试邮件）

## 5. 准出标准（Exit Criteria）

项目可交付上线的最小条件（都必须满足）：

### 5.1 功能完整性
- ✅ AC-001~AC-007 全部通过（0 个阻断 bug）
- ✅ 所有关键流程端到端验证通过（竞对创建 → 邮件投递）
- ✅ 错误处理验证通过（网络故障、无效输入、服务超时等）

### 5.2 性能与可靠性
- ✅ 采集成功率 > 95%（7 天测试）
- ✅ 邮件送达率 > 99%（30 次投递测试）
- ✅ 变化检测精准度 > 95%（人工审查 50+ 条变化记录）
- ✅ API P95 响应时间 < 200ms（竞对列表查询）
- ✅ 系统无严重性能瓶颈（10 竞对采集不超时）

### 5.3 质量与文档
- ✅ 代码审查通过（所有 P0/P1 问题已修复）
- ✅ 测试覆盖率 >= 80%（关键路径 > 90%）
- ✅ 文档完整（README、runbook、API 文档）
- ✅ 无遗留 P1 级及以上缺陷

### 5.4 用户验收
- ✅ 用户可用性测试通过（NPS >= 50，易用性评分 >= 4/5）
- ✅ 内容质量验收（日报准确、完整、格式正确）
- ✅ 无影响用户体验的 bug（P0/P1）

### 5.5 阻断交付的条件（Red Lines）

以下任一情况发生，**禁止发布**：

🔴 **阻断 1**：AC-001~AC-007 中任一不通过  
🔴 **阻断 2**：采集成功率 < 95%（无法满足基本可靠性）  
🔴 **阻断 3**：邮件送达率 < 95%（核心功能失效）  
🔴 **阻断 4**：存在 P0 级 bug（系统崩溃、数据丢失、安全漏洞）  
🔴 **阻断 5**：性能基准未达标（API 响应 > 500ms 或采集超时 > 30s）
