# Lensmor Monitor v1.0.0 测试用例清单

## 使用说明

本文档列出所有测试用例（Use Case），按 AC（Acceptance Criteria）和测试类型分类。

- **执行人**：QA + 工程师
- **工具**：手工测试 + Postman / curl（API）+ Jest（自动化）
- **执行时间**：预计 3–5 天
- **记录方式**：在 `verification/report.md` 中按 Use Case ID 记录结果

---

## 1. 竞对列表管理（AC-001）

### UC-001-01: 创建竞对

**目的**：验证用户能成功创建竞对

**前置条件**：
- 前端已加载竞对列表页（P-001）
- 后端 API 正常运行

**操作步骤**：
1. 点击"+ 新增竞对"按钮
2. 填写表单：名称 = "Test Competitor"，URL = "https://example.com"，备注 = "测试竞对"
3. 点击"保存"按钮

**预期结果**：
- ✅ 表单消失，返回竞对列表
- ✅ 新竞对出现在列表中（ID、名称、URL、创建时间）
- ✅ 后端返回 201 Created

**验证点**：
- [ ] 前端立即刷新列表
- [ ] 数据库 `competitors` 表有新记录
- [ ] 新竞对 active = true

**责任人**：QA  
**Priority**：P0  
**Status**：⬜ Pending

---

**预期结果**：
- ✅ 表单不提交，显示错误提示"竞对名称不能为空"
- ✅ 按钮保持可点击状态

**验证点**：
- [ ] URL 格式验证（输入 "invalid-url"，应拒绝）
- [ ] 备注字段限制 500 字（输入 501 字，应限制）

**责任人**：QA  
**Priority**：P0

### UC-001-04: 删除竞对

**目的**：验证删除功能和二次确认

**操作步骤**：
1. 点击竞对行的"删除"按钮
2. 确认弹窗出现，显示风险提示"删除后将停止监控该竞对，但历史日报数据保留"

**预期结果**：
- ✅ 竞对从列表移除

- ✅ 数据库 `competitors` 表该记录被删除（cascade）

**验证点**：
- [ ] 点击"取消"不删除
- [ ] 关联的 `data_snapshots` 和 `changes` 记录也被删除

**责任人**：QA  
**Priority**：P0  
**Status**：⬜ Pending

## 2. 数据采集（AC-002）

### UC-002-01: 定时采集任务执行

**目的**：验证采集任务在预定时间执行

**前置条件**：
- 已添加 3–5 个竞对
- 后端服务已启动（定时任务已注册）

**操作步骤**：
1. 等待每天 02:00（或手动触发采集）
2. 查看后端日志输出

**预期结果**：
- ✅ 日志显示 "[COLLECT] Starting data collection task..."
- ✅ 日志显示 "Task completed: 3/3 competitors collected (100% success rate)"
- ✅ 数据库 `data_snapshots` 表有新记录

**验证点**：
- [ ] 采集成功率 >= 95%（7 天测试，至少 6.65 天成功）
- [ ] 每个采集快照包含 title、content_hash、url 等字段

**责任人**：后端工程师  
**Priority**：P0  
**Status**：⬜ Pending

---

### UC-002-02: 采集失败重试

**目的**：验证采集失败时的重试机制

**操作步骤**：
1. 添加一个无效的竞对 URL（如 "https://invalid-domain-12345.com"）
2. 等待采集任务运行

**预期结果**：
- ✅ 采集尝试 3 次，每次间隔递增（1s → 2s → 4s）
- ✅ 最终失败后记录到 `data_snapshots` 表（error 字段）

**责任人**：后端工程师  
**Priority**：P1  
**Status**：⬜ Pending

## 3. 变化检测（AC-003）

### UC-003-01: 完全一致比对

**目的**：验证变化检测逻辑

**前置条件**：
- 已有 2 天的采集快照（Day 1 和 Day 2）
- Day 2 快照中某字段已修改

**操作步骤**：
1. 等待每天 02:30（或手动触发变化检测）
2. 查看后端日志和数据库

**预期结果**：
- ✅ 日志显示 "[DETECT] Change detection task started..."
- ✅ `changes` 表有新记录，包含：
  - competitor_id
  - field_name（修改的字段）
  - old_value / new_value
  - change_type（pricing/content/structure/other）

**验证点**：
- [ ] 无修改的竞对不产生 change 记录
- [ ] 多字段修改产生多条 change 记录

**责任人**：QA + 后端工程师  
**Priority**：P0  
**Status**：⬜ Pending

---

### UC-003-02: 变化精准度验证

**目的**：人工验证变化检测的准确性

**操作步骤**：
1. 收集 14 天的变化检测结果（50+ 条变化记录）
2. 人工审查每条变化，确认字段变化是否真实

**验证标准**：
- 精准度 = （正确的变化 / 总变化）>= 95%
- 误报率 = （虚假的变化 / 总变化）< 5%
- 遗漏率 = （未检出的真实变化 / 真实变化总数）< 5%

**责任人**：QA  
**Priority**：P1  
**Status**：⬜ Pending

## 7. 性能测试（AC-007）

## 8. 用户验收测试（V-004）

### UC-008-01: 用户易用性测试

**目的**：验证 UI 易用性和内容质量

**参与者**：5 位内部用户（产品/运营团队）

**测试时长**：7 天

**评估维度**：
1. 易用性评分（1–5 分）：能否轻松找到功能、操作是否直观
2. 内容质量评分（1–5 分）：日报信息是否有用、是否清晰
3. NPS 评分：会否推荐给他人

**成功标准**：
- ✅ 易用性 >= 4/5
- ✅ 内容质量 >= 4/5
- ✅ NPS >= 50

**收集方式**：问卷 + 访谈

**责任人**：产品经理
